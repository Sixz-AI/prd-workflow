# PRD 分解技能（中文参考）

> **注意：** 本文件为中文翻译版，仅供人工阅读。AI Agent 请以 `SKILL.md`（英文）为准。

## 概述

本技能将复杂的 PRD（产品需求文档）转化为纯结构化文档——一套定义了最优粒度需求单元（REQ）的 Markdown 文件集合，输出到项目的 `docs/` 目录下。

**核心聚焦：** 高质量的拆解专注于 **"做什么"** 和底层 **业务逻辑**，从不涉及 **"如何编码"**。Agent 主动识别模糊逻辑、确认边界，将逻辑拆解为原子化的可管理单元。

## 使用时机

- 用户提供了新的 PRD 或功能需求文档
- 业务逻辑需要在开发前进行压力测试和澄清
- 需求需要被拆解为原子化的业务逻辑需求单元（REQ）

## 核心原则

> **1. 先澄清，后拆解**
> 永远不要盲目解析定义不清的 PRD。始终与用户互动，确认模糊逻辑、边界条件和边缘情况。
>
> **2. 代码探索是输入，不是输出**
> 当用户提供代码库引用时，**彻底探索代码**以理解现有功能、当前行为和业务上下文。这是你的输入，帮助你准确描述现状。但输出必须用**纯业务语言**表达，绝不在生成的文档中包含文件路径、行号、变量名、函数名或架构模式。
>
> **3. 聚焦业务逻辑（做什么，而非怎么做）**
> 需求拆解严格关于分解**业务逻辑**，不是指导实现方式。清晰说明功能是什么、业务规则是什么。绝不告诉下游 AI "如何编码"。
>
> **4. 现状 → 目标状态 → 差异**
> 每个 REQ 必须清晰描述：今天存在什么（现状）、产品想要什么（需求）、以及精确的差异（变更：增加/修改/删除）。
>
> **5. 基于文件的渐进式披露**
> 输出为结构化目录文件，从大纲索引开始，所有文件存放在 `docs/` 目录下。

## 工作流程

### 第一步：代码库探索（静默阶段）
当用户提供代码库引用时，**先彻底探索代码**，再提问。目标是深入理解：
1. **当前业务行为** — 从用户角度看，现有功能做什么？
2. **受影响的功能** — 哪些现有功能会被新需求影响？
3. **业务边界** — 当前逻辑从哪里开始和结束？
4. **PRD 中的空白** — PRD 假设或遗漏了哪些业务细节？

### 第二步：多角色 PRD 分析与边界澄清（交互阶段）
模拟多代理专家小组审查业务逻辑：
1. **QA 工程师角色：** 识别缺失的不幸路径、空状态、加载状态、特定权限、未处理的边缘情况
2. **资深架构师角色：** 评估数据流边界、系统交互和潜在竞态条件
3. **产品经理角色：** 确认核心业务循环，确保没有用户价值丢失

**[硬性关卡 1：反合理化检查清单]**
必须输出检查清单确认已完成多视角审查。在用户明确批准前，**严禁生成任何文件**。

### 第三步：规划质量审查与需求整合
整合用户的补充答案。
**[硬性关卡 2：规划质量审查]**
确保业务逻辑符合 MECE（相互独立、完全穷尽），每个变更都有清晰的"现状"和"目标状态"，验收标准以可观察的用户行为定义。

### 第四步：全局扫描与大纲生成

**[目标项目配置]**
在生成任何文件之前，询问用户目标项目的绝对路径。确认后执行两步初始化：
1. 将 `prd_executor` skill 复制到 `[目标项目]/.claude/skills/prd_executor/`（已存在则跳过）
2. 运行脚本在 `[目标项目]/docs/[功能名称]_breakdown/` 下初始化 `README.md`

所有后续产物均输出到 `[目标项目]/docs/[功能名称]_breakdown/` 下。

生成 `[目标项目]/docs/[功能名称]_breakdown/outline.md` 作为宏观大纲索引，**包含 Status 列**，所有 REQ 默认状态为 `⬜ 未开始`。

### 第五步：生成单个 REQ 文档
在 `[目标项目]/docs/[功能名称]_breakdown/reqs/` 下为每个 REQ 创建独立 Markdown 文件。

每个 REQ 文件顶部必须包含（按顺序）：
1. `📊 执行状态` 表格（默认 ⬜ 未开始）
2. `🔍 详细需求确认` 占位符（含 10 个闭环维度，**分解阶段不得预填充**）
3. 现有的现状/需求/变更/验收标准内容

**[硬性关卡 3：完成前验证]**
每个 REQ 必须包含以"用户做 X → 系统显示/执行 Y"格式编写的验收标准，涵盖正常路径和异常路径。

## 输出文档结构

```
docs/[功能名称]_breakdown/
├── README.md            # 执行指南 + Git 工作流规范（模板自动生成）
├── outline.md           # 宏观大纲索引（含 Status 列）
└── reqs/
    ├── REQ-1.1.md       # 含执行状态 + 需求确认占位符
    └── REQ-X.X.md
```

## 注意事项

1. **不要指导代码** — 不在输出文档中包含文件路径、变量名、函数名
2. **不要抢先！** — 在用户澄清模糊业务逻辑前，不生成文档
3. **上下文隔离** — 每个 REQ 文件只包含该 REQ 的业务逻辑
4. **代码是输入，不是输出** — 生成的文档必须用业务/产品语言描述
5. **不要纯重构 REQ** — 每个 REQ 必须描述用户可见的业务行为变化
6. **现状必须准确** — 用可观察的用户行为描述现状，不用代码结构描述
