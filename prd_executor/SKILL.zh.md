# PRD 执行技能（中文参考）

> **注意：** 本文件为中文翻译版，仅供人工阅读。AI Agent 请以 `SKILL.md`（英文）为准。

## 概述

本技能引导 Dev Agent 执行 `prd_decomposer` 生成的 `docs/[功能名称]_breakdown/` 目录中的 breakdown，强制执行三个硬性关卡：

1. 在任何编码开始前完成需求确认（头脑风暴 10 个闭环维度）
2. 实现过程中遵循 TDD 工作流
3. 每完成一个 REQ 执行 commit，每完成一个 Phase 执行 push

## 使用时机

- `docs/[功能名称]_breakdown/` 目录已存在
- 用户说"开始执行"、"开始开发"、"实现这个 PRD"、"执行 breakdown"
- Dev Agent 拿到一个 breakdown 目录，需要知道如何推进

## 工作流程

### 第一步：初始化

读取 `docs/[功能名称]_breakdown/outline.md`，提取：
- Phase 和 REQ 总数
- REQ 之间的依赖关系图
- 每个 REQ 的当前状态（查看 Status 列）

向用户宣布：哪些 REQ 待处理，哪些（如有）正在进行或已完成。

### 第二步：选择下一个 REQ

找到第一个状态为 ⬜（未开始）且所有依赖项都是 ✅ 或 ⚠️ 的 REQ。

如果不存在这样的 REQ：
- 如果所有 REQ 都是 ✅ 或 ⚠️：宣布完成，为未推送的 Phase 执行 `git push`，结束。
- 如果某些 REQ 是 🚧 进行中：从第三步恢复该 REQ。
- 如果某些 REQ 是 🚫 搁置：跳过，找下一个合适的 REQ。

### 第三步：需求确认（硬性关卡 1）

打开 REQ 文件，定位 `🔍 详细需求确认` 部分。

**检查：** 该部分是否仍包含 `⚠️ [待填充]` 占位符文本？

**如果是（占位符存在——确认未完成）：**

1. 将 REQ 文件状态从 ⬜ 更新为 💬（需求讨论中）
2. 将 `outline.md` 中对应行的 Status 列更新为 💬
3. 以 REQ 内容为上下文调用 `superpowers:brainstorming`
4. 头脑风暴过程中确保覆盖所有 10 个闭环维度：
   - API 闭环
   - 业务逻辑闭环
   - UI/UX 闭环
   - 错误处理闭环
   - 数据一致性闭环
   - 权限/安全闭环
   - 性能边界闭环
   - 测试闭环（单测场景 + 手动 UAT 验收点）
   - 埋点/打点闭环
   - 兼容性闭环
5. 头脑风暴完成后，用分析结论替换整个占位符块
6. **在占位符被替换之前，严禁编写任何实现代码**

**如果否（占位符已替换——确认已完成）：**
跳至第四步。

### 第四步：开始实现

1. 将 REQ 文件状态从 💬 更新为 🚧（执行中）
2. 将 `outline.md` 中对应行更新为 🚧
3. 以 REQ 的验收标准为测试目标调用 `superpowers:test-driven-development`

**以下情况不需要 commit：**
- 调试过程
- Mock 数据设置
- 添加/删除 console.log 或临时日志
- 尚未通过验收标准的未完成功能

### 第五步：完成 REQ（硬性关卡 2）

当 REQ 主功能完成且验收标准满足时：

1. 更新 REQ 文件状态：
   - **✅ 已完成** — 所有验收标准经手动 UAT 验证通过
   - **⚠️ 部分完成** — 主功能可用，部分 AC 条目搁置（在备注字段写明原因）
   - **🚫 已搁置** — 完全受阻（在备注字段写明原因，移至下一个 REQ）

2. 将 `outline.md` 中对应行同步更新

3. 将 REQ 文件执行状态表中的 `最后更新` 字段更新为今日日期

4. 提交：
   ```bash
   git add -p   # 仅暂存实现文件，不包含调试/Mock 产物
   git commit -m "feat(REQ-X.X): [简短描述构建了什么]"
   ```

### 第六步：检查 Phase 完成情况

每次 commit 后，检查刚完成 REQ 所在的 Phase。

**该 Phase 的所有 REQ 都是 ✅ 或 ⚠️？**

是 → 推送：
```bash
git push
```
然后返回第二步处理下一个 Phase。

否 → 返回第二步处理本 Phase 的下一个 REQ。

## 状态说明

| 状态 | Emoji | 含义 |
| ---- | ----- | ---- |
| 未开始 | ⬜ | 分解时的默认状态 |
| 需求讨论中 | 💬 | 头脑风暴进行中 |
| 需求变更 | 🔄 | 确认后需求有修改（在备注中记录变更内容和原因） |
| 执行中 | 🚧 | 实现进行中 |
| 已完成 | ✅ | 所有验收标准已验证 |
| 部分完成 | ⚠️ | 主功能完成，部分 AC 条目搁置（备注中写明原因） |
| 已搁置 | 🚫 | 受阻，见备注说明原因 |

## 处理需求变更（🔄）

如果在 REQ 处于 🚧 执行中时需求发生变化：
1. 将状态设置为 🔄 需求变更
2. 在备注字段记录：变更了什么、为什么、日期
3. 更新 REQ 文件的 `🎯 Requirement` 和 `✅ Acceptance Criteria` 部分
4. 仅对变更的维度重新进行头脑风暴
5. 使用更新后的需求恢复实现

## 注意事项

1. **永远不要跳过占位符检查** — 头脑风暴能发现 PRD 遗漏的边缘情况；跳过会导致返工
2. **状态必须在两处更新** — REQ 文件和 `outline.md` 都必须保持同步
3. **每个 REQ 后 commit，每个 Phase 后 push** — 不要跨多个 REQ 批量 commit
4. **⚠️ 部分完成 ≠ 无文档的完成** — 部分完成的 REQ 必须在备注中写明原因才能计入 Phase 完成
5. **🔄 需求变更会使进行中的工作失效** — 需求变更时，继续实现前需重新确认
