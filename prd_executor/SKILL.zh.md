# PRD 执行技能（中文参考）

> **注意：** 本文件为中文翻译版，仅供人工阅读。AI Agent 请以 `SKILL.md`（英文）为准。

## 概述

本技能引导 Dev Agent 执行 `prd_decomposer` 生成的 `docs/[功能名称]_breakdown/` 目录中的 breakdown，强制执行三个硬性关卡：

1. 在任何编码开始前完成需求确认（头脑风暴 10 个闭环维度）
2. 实现过程中遵循 TDD 工作流
3. 每完成一个 REQ 执行 commit，每完成一个 Phase 执行 push

## 使用时机

- `docs/[功能名称]_breakdown/` 目录已存在
- 用户说"开始执行"、"开始开发"、"实现这个 PRD"、"执行 breakdown"
- Dev Agent 拿到一个 breakdown 目录，需要知道如何推进

## 工作流程

### 第一步：初始化

读取 `docs/[功能名称]_breakdown/outline.md`，提取：
- Phase 和 REQ 总数
- REQ 之间的依赖关系图
- 每个 REQ 的当前状态（查看 Status 列）

向用户宣布：哪些 REQ 待处理，哪些（如有）正在进行或已完成。

### 第二步：选择下一个 Phase

在 `outline.md` 中找到第一个状态为 ⬜（未开始）且所有 REQ 跨 Phase 依赖项（如有）都是 ✅ 或 ⚠️ 的 Phase。

如果不存在这样的 Phase：
- 如果所有 Phase 都是 ✅：宣布完成，结束。
- 如果某个 Phase 是 💬 或 🔍 或 🚧 或 🧪：从下方对应阶段恢复该 Phase。

---

### 阶段 A：讨论 —— 讨论 Phase 内所有 REQ【硬性关卡 1】

1. 将 `outline.md` 中的 Phase 状态更新为 💬（讨论中）
2. 按顺序处理本 Phase 中的每一个 REQ：
   a. 打开 REQ 文件，检查 `🔍 详细需求确认` 部分是否仍包含 `⚠️ [待填充]`。
   b. 如果是（占位符存在）：
      - 将 REQ 文件和 `outline.md` 中的 REQ 状态更新为 💬
      - 以 REQ 内容为上下文调用 `superpowers:brainstorming`
      - 确保覆盖所有 10 个闭环维度：
        - API 闭环
        - 业务逻辑闭环
        - UI/UX 闭环
        - 错误处理闭环
        - 数据一致性闭环
        - 权限/安全闭环
        - 性能边界闭环
        - 测试闭环（单测场景 + 手动 UAT 验收点）
        - 埋点/打点闭环
        - 兼容性闭环
      - 用头脑风暴的结论替换整个 `⚠️ [待填充]` 占位符块
   c. 如果否（占位符已替换）：跳过该 REQ 的头脑风暴。
3. **阶段 A 期间严禁编写任何实现代码**

---

### 阶段 B：汇总确认

1. 将 `outline.md` 中的 Phase 状态更新为 🔍（待确认）
2. 向用户展示所有 REQ 讨论结论的汇总：

   ```
   Phase X 讨论汇总：
   - REQ-X.1 [标题]：[2-3 条关键结论]
   - REQ-X.2 [标题]：[2-3 条关键结论]
   - REQ-X.3 [标题]：[2-3 条关键结论]
   ```

3. 询问用户：**"以上内容是否正确？可以开始实现了吗？"**
4. 等待用户回复：
   - **确认** → 进入阶段 C
   - **对某个 REQ 提出修改** → 仅对该 REQ 重新进行头脑风暴，在 REQ 文件中更新其结论，重新展示完整汇总，然后重复第 3 步（再次等待确认）

---

### 阶段 C：实现 —— 自主完成 Phase 内所有 REQ

1. 将 `outline.md` 中的 Phase 状态更新为 🚧（实现中）
2. 按顺序处理本 Phase 中的每一个 REQ：
   a. 将 REQ 文件和 `outline.md` 中的 REQ 状态更新为 🚧（进行中）
   b. 以 REQ 的验收标准为测试目标调用 `superpowers:test-driven-development`
   c. 当验收标准内部通过时：REQ 状态保持 🚧 —— 将在阶段 G 用户通过 UAT 后更新为 ✅
   d. 每个 REQ 完成后立即提交：
      ```bash
      git add -p   # 仅暂存实现文件，不包含调试/Mock 产物
      git commit -m "feat(REQ-X.X): [简短描述构建了什么]"
      ```
3. **阶段 C 期间不得在任何时间点打断用户**
4. **以下情况不需要 commit：** 调试过程、Mock 数据设置、添加/删除 console.log、尚未通过 AC 的未完成功能

---

### 阶段 D：UAT 通知

1. 将 `outline.md` 中的 Phase 状态更新为 🧪（待 UAT）
2. 根据每个 REQ 的验收标准生成 UAT 检查清单：

   ```
   Phase X UAT 检查清单：

   REQ-X.1 [标题]
   请验证：
   - [ ] [AC 条目 1]
   - [ ] [AC 条目 2]

   REQ-X.2 [标题]
   请验证：
   - [ ] [AC 条目 1]
   - [ ] [AC 条目 2]
   ```

3. 通知用户："Phase X 的所有 REQ 均已实现，请逐项验证上方清单，并告知哪些 REQ 通过、哪些失败（失败请说明原因）。"

---

### 阶段 E：用户 UAT

等待用户报告结果。等待期间，Phase 状态保持 🧪（待 UAT），不修改任何代码。期望格式（用户可用任意自然语言）：
- "REQ-X.1 通过，REQ-X.2 失败 —— [原因]"

---

### 阶段 F：修复循环（仅针对失败的 REQ）

对每个用户报告为失败的 REQ：
1. **不要重新进行头脑风暴** —— 根据用户反馈直接进行修复
2. 修复实现
3. 仅为该 REQ 重新生成 UAT 检查清单：

   ```
   REQ-X.2 [标题] —— 已修复，请重新验证：
   - [ ] [AC 条目 1]
   - [ ] [AC 条目 2]
   ```

4. 请用户仅重新验证该 REQ
5. 重复直到该 REQ 通过
6. 已通过的 REQ 不再触碰
7. 当所有之前失败的 REQ 均已通过，进入阶段 G

---

### 阶段 G：Phase 完成

当 Phase 内所有 REQ 通过 UAT 后：
1. 更新每个 REQ 文件的状态：
   - **✅ 已完成** — 所有验收标准经用户 UAT 验证通过
   - **⚠️ 部分完成** — 主功能可用，部分 AC 条目搁置（在备注字段写明原因）
2. 同步更新 `outline.md` 中对应行
3. 将每个 REQ 文件中的 `最后更新` 字段更新为今日日期
4. 将 `outline.md` 中的 Phase 状态更新为 ✅（已完成）
5. 推送：
   ```bash
   git push
   ```
6. 返回第二步处理下一个 Phase

## 状态说明

| 状态 | Emoji | 含义 |
| ---- | ----- | ---- |
| 未开始 | ⬜ | 分解时的默认状态 |
| 讨论中 | 💬 | 头脑风暴进行中 |
| 需求变更 | 🔄 | 确认后需求有修改（在备注中记录变更内容和原因） |
| 实现中 | 🚧 | 实现进行中 |
| 已完成 | ✅ | 所有验收标准已验证 |
| 部分完成 | ⚠️ | 主功能完成，部分 AC 条目搁置（备注中写明原因） |
| 已搁置 | 🚫 | 受阻，见备注说明原因 |

## Phase 状态说明

| 状态 | Emoji | 含义 |
| ---- | ----- | ---- |
| 未开始 | ⬜ | 默认状态 |
| 讨论中 | 💬 | REQ 头脑风暴进行中 |
| 待确认 | 🔍 | 所有 REQ 已讨论，等待用户签字确认 |
| 实现中 | 🚧 | AI 自主实现所有 REQ |
| 待 UAT | 🧪 | 等待用户验证 |
| 已完成 | ✅ | 所有 REQ 通过 UAT，已推送 |

## 处理需求变更（🔄）

如果在 REQ 处于 🚧 实现中时需求发生变化：
1. 将状态设置为 🔄 需求变更
2. 在备注字段记录：变更了什么、为什么、日期
3. 更新 REQ 文件的 `🎯 Requirement` 和 `✅ Acceptance Criteria` 部分
4. 仅对变更的维度重新进行头脑风暴
5. 使用更新后的需求恢复实现

## 注意事项

1. **永远不要跳过占位符检查** — 头脑风暴能发现 PRD 遗漏的边缘情况；跳过会导致返工
2. **状态必须在两处更新** — REQ 文件和 `outline.md` 都必须保持同步
3. **每个 REQ 后 commit，每个 Phase 后 push** — 不要跨多个 REQ 批量 commit
4. **⚠️ 部分完成 ≠ 无文档的完成** — 部分完成的 REQ 必须在备注中写明原因才能计入 Phase 完成
5. **🔄 需求变更会使进行中的工作失效** — 需求变更时，继续实现前需重新确认
